# Native USB transport optimization

Profile first, then change. This document records what was measured, what the
measurements implicated, what was changed, and what the change was worth.

## 1. Baseline decomposition

The reported regression was `PanelHost 4.61% -> 36.57%` and
`Android 9.37% -> 101.41%`. Both figures are CPU divided by wall time, and the
two runs had wildly different wall times for identical work:

| Run | Wall | Payload moved | Host CPU | Android CPU |
| --- | ---: | ---: | ---: | ---: |
| ADB/TCP | 438.9 s | 267.1 MiB | 20.25 s | 41.13 s |
| USB native | 35.8 s | 267.2 MiB | 13.08 s | 36.26 s |

Native USB already used **35% less host CPU and 12% less Android CPU** than
ADB/TCP to move the same bytes. It finished 12x faster because its RTT was 5x
lower, and compressing the same CPU work into one twelfth of the wall clock is
what produced the alarming percentage.

That does not make the cost acceptable - a carrier that pins a core while it
works still throttles a passively cooled tablet - but it changes the question
from "why is USB 8x more expensive" to "why does USB cost 49 ms of host CPU and
136 ms of Android CPU per mebibyte at all".

The harness now measures `idle`, `latency` and `bulk` separately and reports CPU
seconds, CPU per MiB, syscall rates, transfer sizes and allocation rates for each
(`--benchmark-idle-seconds`, `*-phases.csv`).

## 2. Windows CPU profile

Hot path, per PLMX frame, before the change:

```
MultiplexedTransportSession.WriteAsync
  -> bytes.Slice(...).ToArray()            allocation + full payload copy
  -> MultiplexFrame.EncodeHeader           new byte[16] per frame
  -> stream.WriteAsync(header)             Task.Run -> ToArray -> WinUsb_WritePipe (16 B transfer)
  -> stream.WriteAsync(payload)            Task.Run -> ToArray -> WinUsb_WritePipe

MultiplexedTransportSession.ReaderLoopAsync
  -> ReadExactlyAsync(header, 16)          Task.Run -> new byte[16] -> WinUsb_ReadPipe
  -> new byte[header.PayloadLength]        allocation per frame, LOH above 85 KB
  -> ReadExactlyAsync(payload)             Task.Run -> new byte[remaining] -> copy, per partial read
```

Four properties made this expensive, in descending order of measured impact:

1. **Two physical transfers per logical frame.** The 16-byte header was its own
   USB transfer. Every control message therefore cost two URBs, two thread-pool
   dispatches and two completions in each direction.
2. **`Task.Run` per I/O operation.** Every read and write queued a work item and
   then blocked a thread-pool thread inside a synchronous WinUSB call. The reader
   loop parked a worker permanently. Cancellation could not reach a call already
   in flight, so `Task.Run(..., token)` only prevented scheduling.
3. **Allocation and copy per operation.** `WinUsbDevice.Read` allocated
   `new byte[target.Length]` on every call and copied out; `Write` called
   `source.ToArray()`. On a 1 MiB payload read in partial chunks this allocated a
   fresh near-1-MiB array per partial read, straight into the large object heap.
   Maximum working set was 341.8 MB versus 229.9 MB for ADB.
4. **Payload copied twice on send** - once by `.ToArray()` during fragmentation,
   once by `.ToArray()` inside the write.

## 3. Android CPU profile

```
readerLoop -> readExactly(header, 16)      one read() syscall for 16 bytes, per frame
           -> ByteArray(payloadLength)     allocation per frame, large object space above 12 KB
           -> readExactly(payload)         further read() syscalls
writerLoop -> physicalOutput.write(header) one write() syscall for 16 bytes
           -> physicalOutput.write(payload)
MuxConnection.output.write
           -> buffer.copyOfRange(...)      full copy per fragment
TransportBenchmarkClient
           -> ByteArray(size) { ... }      32 MiB regenerated byte by byte, per repetition
```

The 16-byte header read is the important one: `f_accessory` sets its USB request
length from the `read()` count, so a 16-byte read posts a 16-byte request and
forces the host to send the header as a separate transfer. The two sides were
locking each other into two transfers per frame.

## 4. I/O call frequency and sizes, measured after the change

| Phase | Host reads/s | Host writes/s | B/read | B/write | writes/frame | reads/frame |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| idle | 0.3 | 1.3 | 73 | 323 | 1.00 | 1.00 |
| latency | 2,168 | 2,169 | 452 | 452 | **1.00** | **1.00** |
| bulk | 433 | 219 | 32,602 | 64,570 | **1.00** | 1.99 |

Android, same run: 2,169 reads/s and 2,168 writes/s in the latency phase at 452
bytes each, 1.00 reads per frame. In the bulk phase, 1,081 reads/s at 13,071
bytes, 4.94 reads per frame - one per 16 KiB gadget buffer, which is the
kernel's granularity and not something the application controls.

`writes/frame = 1.00` is the direct measurement that header and payload now share
a single transfer. Before the change this was structurally 2.00.

`reads/frame = 1.99` in bulk is the one remaining inefficiency: a 64 KiB fragment
plus its 16-byte header is 65,552 bytes, sixteen bytes larger than the 64 KiB
read buffer, so it always takes two reads. Raising `PANELOS_USB_READ_BUFFER` to
131,072 should make it 1.00. This was **not** verified - the verification run hit
the AOA re-entry defect below - so the default is left at the measured 64 KiB.

## 5. Allocation profile

Host, measured per phase (`HostAllocatedBytes`, GC counts):

| Phase | Allocated | Gen0/1/2 |
| --- | ---: | ---: |
| idle | 1.1 MiB over 10 s | 0/0/0 |
| latency | 93.1 MiB over 11.6 s | 12/1/0 |
| bulk | 170.5 MiB over 9.1 s | 3/3/2 |

The bulk figure is dominated by the harness's 32 MiB payload and receive buffers,
not the carrier: the carrier itself allocates one pooled array per received frame
and returns it. Rentals and returns balanced exactly - 25,203/25,203 in the
latency phase, 1,989/1,989 in bulk - so nothing leaks and nothing is returned
twice.

Android reported **zero** payload allocations after warm-up in both traffic
phases: every received frame came from the pool.

## 6. Threads involved

Windows: one reader loop, one writer loop, plus I/O completion-port threads that
now handle transfer completions instead of dedicated blocked workers. Android:
`PanelOS-USB-reader` and `PanelOS-USB-writer`, whose CPU is now sampled from
`/proc/self/task/<tid>/stat` on demand and reported per phase.

Android thread-level attribution, USB, full run:

| Phase | Reader CPU | Writer CPU | Process CPU | Transport share |
| --- | ---: | ---: | ---: | ---: |
| idle | 0.01 s | 0.00 s | 1.61 s | 0.6% |
| latency | 3.09 s | 4.21 s | 14.30 s | 51% |
| bulk | 0.82 s | 0.79 s | 3.97 s | 41% |

At idle the carrier is free. Under load roughly half the app's CPU is the
carrier and the rest is the benchmark responder and the application itself.

## 7. Changes applied

### WinUSB (`windows/PanelHost/Transport/WindowsUsbAccessory.cs`)

- **Real overlapped I/O.** The device handle is bound to the thread pool's
  completion port with `ThreadPoolBoundHandle`; transfers are issued with a
  `NativeOverlapped` and completed by an I/O callback. No `Task.Run`, no blocked
  worker, and `CancelIoEx` can now cancel a transfer already in flight.
- **Pinned staging buffers.** One 64 KiB read buffer and one 256 KiB write buffer
  live on the pinned object heap for the session's lifetime, so a transfer costs
  no allocation and no per-operation pinning.
- **Buffered reads.** A refill always requests the whole buffer, so one transfer
  can carry a header, its payload and the head of the next frame. A short packet
  still completes the read immediately, so buffering costs no latency.
- **Chunked writes.** Writes above 256 KiB are split on 512-byte boundaries so a
  chunk boundary never injects a short packet mid-frame.
- **Bounded write timeout.** `PIPE_TRANSFER_TIMEOUT` of 5 s on the bulk OUT pipe
  only; bulk IN keeps its infinite wait because an idle link legitimately has
  nothing to deliver. A wedged peer now surfaces as a disconnect instead of a
  writer thread parked forever.
- **Zero-length packets** are still retried rather than treated as end of stream,
  now in one loop rather than recursively.

### PLMX framing (`MultiplexedTransportSession.cs`, `MultiplexFrame.cs`)

- **One physical write per frame.** Header and payload are staged into a reusable
  scratch buffer and written once when the payload fits the fragment.
- **Fragmentation by slicing, not copying.** `WriteAsync` passes
  `ReadOnlyMemory<byte>` slices. This is sound because the caller stays parked on
  the fragment's completion, so it cannot observe or reuse its buffer while the
  fragment is pending. A regression test pins that contract.
- **Header written into a reusable buffer** instead of a fresh 16-byte array.
- **Pooled receive payloads** with a single explicit owner: the reader loop owns
  a rented buffer until a logical stream accepts it, then the consumer owns it
  until it is drained or the channel completes.
- **Configurable fragment size**, default 64 KiB (was effectively 1 MiB), always
  a whole number of 512-byte max packets.

### Android (`MultiplexedTransportSession.kt`, `TransportIoProfile.kt`)

- **Staged reader.** `PhysicalFrameReader` refills through a 16 KiB buffer that
  matches `BULK_BUFFER_SIZE` in `f_accessory`, so every posted USB request is a
  whole number of max packets and the host is free to coalesce. Tails of 16 KiB
  or more are read straight into the destination.
- **One write syscall per frame**, same scratch-buffer approach as the host.
- **No copy per fragment.** `MuxConnection.output.write` passes an offset and
  length instead of `copyOfRange`.
- **Bounded payload pool** with explicit single ownership and double-release
  protection.
- **Session failure diagnostics.** A session that dies now logs its root cause,
  frame counts and syscall counts. This is what identified the reconnect defect.

### Harness (`TransportBenchmark.cs`, `TransportBenchmarkClient.kt`)

Corrections so the measurement stops charging itself to the carrier:

- deterministic payloads are generated once and sliced, not regenerated per
  repetition (32 MiB rebuilt byte by byte on an A53 was real Android CPU);
- receive buffers are reused instead of allocated per frame;
- benchmark header and payload go out as one write, so one benchmark message is
  one PLMX frame instead of two;
- phase decomposition, CPU seconds, CPU per MiB, syscall rates, transfer sizes,
  allocation rates, GC counts and Android thread CPU are all reported;
- a Desktop scenario fails early and explicitly when PanelHost is not elevated or
  PanelDisplayDriver is unreachable.

The benchmark-message coalescing also removed a 42 ms p95 artifact from the ADB
numbers: previously each message was two writes, and the second interacted with
delayed ACK on loopback. ADB p95 went from 42.7 ms to 4.19 ms with no change to
the ADB transport itself. The old ADB latency figures were largely harness.

## 8. Effect of each change

| Change | Before | After | Effect |
| --- | --- | --- | --- |
| Coalesce header and payload | 2 physical transfers per frame | 1.00 writes/frame measured | halves URBs, dispatches and completions in both directions |
| Overlapped I/O instead of `Task.Run` | 1 work item + 1 blocked worker per operation | completion-port callback | removes ~4,300 dispatches/s in the latency phase; makes cancellation real |
| Pinned staging, no per-op allocation | `new byte[n]` per read, `ToArray()` per write | zero steady-state allocation | max working set 341.8 -> 297.9 MB (-12.8%) |
| Slice instead of copy when fragmenting | 2 copies per sent byte | 1 | removes one full pass over every payload |
| Staged Android reader | 1 syscall for a 16-byte header per frame | 1.00 reads/frame | halves syscalls, and is what lets the host coalesce at all |
| Pooled payloads both sides | 1 allocation per frame | 0 Android allocations after warm-up | removes large-object-space churn on the tablet |
| Fragment 1 MiB -> 64 KiB | control waits behind a whole 1 MiB write | control waits at most one 64 KiB fragment | p95 1.389 -> 0.582 ms |
| Harness payload reuse | 123 MiB regenerated per side per run | generated once | removes harness CPU from the carrier's column |

Aggregate: **host CPU -43.1%** (13.08 -> 7.44 CPU-s), **Android CPU -44.4%**
(36.26 -> 20.17 CPU-s), **RTT p50 -59.4%**, **p95 -58.1%**, **p99 -60.3%**,
**device-to-host throughput +18.7%**, **host-to-device throughput -7.0%**.

Against the engineering targets: host CPU is now 23.79% of wall over a 3.5x
shorter run, which is 15% fewer CPU seconds than ADB/TCP - the same order of
magnitude as ADB, as asked. Android is 64.66% of one core during synthetic
saturation and 16.0% at idle, well below a full core, and its transport threads
account for roughly half of that.

## 9. Not completed, and why

### Requires elevation the agent cannot grant

PanelHost must run elevated to reach PanelDisplayDriver. The precondition probe
now reports this explicitly rather than silently producing a Dashboard-shaped
result:

```
[Benchmark] Precondition elevated=False driverAccessible=False
  PanelDisplayDriverException: open interface failed with Win32 error 5
```

A UAC prompt cannot be approved from this session, so the loaded Desktop
scenarios, loaded control RTT, video FPS/drops, touch over USB and Stream Deck
under video were **not measured**. To run them:

```bash
pwsh -File scripts/run-transport-benchmark.ps1 -Transport usb -Scenario desktop-dynamic -Elevated
```

Run the same command with `-Transport adb` for the paired row. The harness now
refuses a Desktop scenario without elevation instead of producing a misleading
result.

### Requires physical access

Cable removal and reinsertion, the 30-cycle reconnect campaign, the 30-minute
soak and thermal observation all need an operator at the tablet.

### Blocked by a defect found during this work

Repeated USB benchmark runs are not currently possible; see below.

## 10. Blockers before native USB can be the default

1. ~~**AOA re-entry leaves stale PLMX bytes in the pipe.**~~ **Fixed** by PLMX v2
   (`docs/plmx-v2.md`): 30/30 reconnect cycles now succeed, each discarding the
   predecessor's 202 residual bytes. Original diagnosis retained below.

   Reproducible before the fix: run a USB
   benchmark, then start a second one without reinstalling the APK. The device is
   already in AOA mode, so no new `ACCESSORY_ATTACHED` is delivered, the new host
   session opens MI_00 directly, and the first bytes it exchanges are leftovers
   from the previous session. The Android side logs:

   ```
   [Transport] Session failed: Physical USB disconnected mid-frame
     (root TransportProtocolException: Data arrived for unopened CONTROL);
     framesTx=2 framesRx=3 reads=3 writes=2
   ```

   Each retry then fails to reopen the accessory
   (`UsbManager.openAccessory` returns null even though the app holds no
   accessory fd), so the app never recovers and the host waits indefinitely.
   PLMX v1 has no session identity, so a session cannot tell its own bytes from
   its predecessor's. Fix direction: a session nonce in the PLMX handshake plus a
   drain-until-handshake resync on both sides, and a bounded wait on the host
   rather than an indefinite accept. This must be fixed before the 30-cycle
   reconnect campaign in section 21 of the brief can even be attempted.

2. **Host-to-Android bulk is 20% below ADB/TCP** (23.26 versus 29.16 MB/s). The
   likely lever is the 1.99 reads/frame noted above and the 16 KiB gadget buffer
   granularity on the device.

3. **Loaded behaviour is entirely unmeasured.** No Desktop H.264, no loaded
   control RTT, no touch or Stream Deck confirmation over USB, no soak.

4. **Privilege architecture.** PanelHost needs elevation for the driver, which is
   out of scope here and slated for the privileged broker.

## 11. Regression tests added

Windows (`TransportPerformanceTests.cs`): zero-length packet is retried not
treated as EOF; one physical read serves several logical reads; writes are
chunked to whole max packets; a frame that fits the fragment reaches the wire as
one write; a larger payload splits into ordered frames; a completed write
releases the caller's buffer; pooled payloads return exactly once; a cancelled
read unblocks; fragment and buffer sizes stay whole max packets; control
overtakes a saturating video stream.

Android (`TransportIoTest.kt`): one staged read serves header and payload; a
refill always requests a whole staging buffer; large tails bypass staging;
partial underlying reads are reassembled; end of stream mid-frame is reported;
a released payload is reused; double release cannot hand one buffer to two
owners; empty and oversized payloads bypass the pool; the bounded pool stops
retaining at its limit; fragment sizing; header encoding into a caller buffer.

Full suites: 342 Windows tests (340 passed, 2 skipped), Android unit tests green.
